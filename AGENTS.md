# Dependency Manager — Project Context

A browser-based tool for managing npm dependencies across multiple local projects (yarn/npm/pnpm/bun). React frontend + Fastify API backend.

## Tech Stack

- **Runtime**: Node.js
- **Frontend**: React 19, Mantine UI, MobX (presenters only), mobx-react-lite
- **Backend**: Fastify, SQLite via @libsql/client + Drizzle ORM
- **Package Manager**: Yarn 4 (Berry) with `node-modules` linker
- **Language**: TypeScript 7 (strict mode, ESM)
- **DI**: `@webiny/di` for dependency injection
- **Stdlib**: `@webiny/stdlib` for UUID generation
- **Shell commands**: execa (wrapped in CommandRunner abstraction)
- **Linter**: oxlint (not ESLint)
- **Formatter**: oxfmt (not Prettier)
- **Test Runner**: Vitest
- **Dependency Audit**: adio (checks unused/missing deps)
- **Build**: tsc for API, Vite for UI

## Commands

- `yarn dev` — start API (port 3001) + Vite dev server (port 5173) with proxy
- `yarn dev:api` — start API server only
- `yarn dev:ui` — start Vite dev server only
- `yarn start` — production: serve API + static UI on single port
- `yarn build` — compile TypeScript (`tsc -b`, outputs to `dist/`)
- `yarn build:ui` — build UI with Vite (outputs to `dist/ui/`)
- `yarn lint` — lint with oxlint (must pass with `--deny-warnings`)
- `yarn lint:fix` — auto-fix lint issues
- `yarn format:check` — check formatting with oxfmt
- `yarn format:fix` — auto-fix formatting
- `yarn test` — run vitest (config in `testing/vitest.config.ts`)
- `yarn test:coverage` — run vitest with v8 coverage
- `yarn adio` — check for unused/missing dependencies
- `yarn full` — adio + lint:fix + format:fix + build + test (full pipeline)

## Path Aliases

Subpath imports via package.json `imports` with conditional resolution:

- `#api/*` — `src/api/*` (dev) / `dist/api/*` (prod)
- `#ui/*` — `src/ui/*` (dev) / `dist/ui/*` (prod)
- `#shared/*` — `src/shared/*` (dev) / `dist/shared/*` (prod)
- `#testing/*` — `src/testing/*` (always source)

## Code Style

- Formatter: oxfmt — 4-space indent for `.js`/`.ts`/`.tsx`, 2-space default
- Print width: 100
- Double quotes, trailing comma: none, arrow parens: avoid
- Linter: oxlint with TypeScript and React plugins
- Curly braces always required (`curly: error`)
- PascalCase for all domain/infrastructure subfolders in `ui/` (features/, presentation/, infrastructure/)
- Top-level dirs (`ui/`, `api/`, `shared/`, `testing/`) stay lowercase
- `infrastructure/` groups UI infra: HttpClient, Events, WebSocket, Shared

## Architecture

### API Layer

- **UseCase pattern**: every route handler delegates to a UseCase (resolve from DI → execute() → Result.match). Use cases return `Result<Data, Error>` from `@webiny/stdlib` (re-exported via `#shared/index.js`). Error types are discriminated unions (`interface IErrors { notFound: ...; unexpected: ... }; type Error = IErrors[keyof IErrors]`). Sequential try/catch (no nesting). One file per abstraction, one file per implementation, never combined.
- **Query services**: complex SQL extracted from routes into PackageQueryService, VulnerabilityQueryService, LicenseQueryService (DI singletons in services/)
- Services are plain DI-wired classes (SecurityService, ScanService, PackageManagerService, etc.)
- **Zod rule**: always use `safeParse()`, never `parse()` — validation must not throw. Handle `!parsed.success` explicitly.
- Routes use `registerRoute(app, routeDef, opts, handler)` with shared Zod-validated route definitions from `src/shared/routes/`
- Response helpers accept `Result` and handle errors internally: `sendOne({ reply, request, result })` wraps value in `{item}`, `sendList({ reply, request, result })` forwards result.value, `sendNone({ reply, request, result, status? })` returns `{success:true}` or 204, `sendError({ reply, request, error: SendableError })` returns `{error:{code, message}}`. All delegate error handling to `sendError` with `SendableError` interface (`code`, `message`, `statusCode?`, `data?`, `stack?`). Routing abstractions: `SendableError`, `RoutingOptions`, `ErrorLoggerHook`, `getRoutingOptions` in `src/shared/routing/abstractions/`
- JobWorker (decomposed: JobQueryHelper, JobRecoveryHelper): concurrent job execution, handles job types: `dependency`, `transient`, `packageManager`, `scan`, `package-scan`, `vulnerability-scan`, `license-scan`, `graph-refresh`, `clone`, `install`, `changelog`, `auto-fix-pr`, `transitive-resolve`. `recoverStaleJobs()` marks any running/pending jobs as `"interrupted"` (not `"failed"`) on server startup with logs "Job interrupted by server restart" — UI shows orange badge, filterable status, distinct from actual failures. Jobs use `referenceId` + `referenceType` instead of `projectId` — project jobs have `referenceType: "project"`, changelog jobs have `referenceType: "package"` with `referenceId = packageName`. AbortController per running job — `cancelJob` aborts running or marks pending as cancelled. `drain()` resolves when all in-flight jobs complete (deterministic test helper + graceful shutdown). Services accept optional `signal?: AbortSignal` threaded to execa via CommandRunner. Chained transient refresh extracts package names from the dependency job and passes them through for targeted refresh. Parent job tracking: `parentJobId` nullable column on `upgradeJobs` — set automatically by chaining methods (dependency→transient, install/dependency/transient→scan, scan orchestrator→child jobs). Error logging includes full stack trace. Orchestration methods: `waitForJob(input)` polls job status every 200ms until terminal, `waitForJobs(input)` waits for multiple jobs concurrently, `getRunningJobsForReference(input)` queries running jobs by referenceId+type. Job log writes are buffered — `appendLog` accumulates in memory, flushes to DB every 2 seconds via timer, WebSocket broadcast stays per-line instant. `finishJob` persists full logs regardless. Progress DB writes throttled to 1/sec. Both log-flush and progress-write catch blocks log errors via Logger abstraction (best-effort — job continues on DB failure).
- JobExecutorRegistry: strategy pattern — maps job type to executor. Executors validate their packages JSON with Zod (no unsafe casts). Adding a new job type = one executor class + register in `JobExecutorRegistry` constructor.
- InstallJobExecutor: runs PM install via driver's `installCommand(flags)`. Validates flags against `driver.installFlags()` using dynamic Zod enum. Checks PM binary exists before running. Broadcasts `install:complete` on success.
- CloneJobExecutor: runs `git clone` via CommandRunner, registers project via `registerProject` helper, stores projectId in job packages for downstream scan enqueue. URL validated (https/git@ only) with `--` end-of-options for argument injection prevention.
- `registerProject` helper (`src/api/services/registerProject.ts`): shared logic for project registration (read package.json name, detect PM, get version, insert DB). Used by create-project route, import route, and CloneJobExecutor. Gracefully handles missing lockfiles (packageManager: null).
- ScanService: workspace-aware, PM-aware, concurrent registry lookups (batches of 10), in-flight dedup via RegistryCacheService, `onProgress` callback for per-package progress. Uses `LockfileParserService` (not CLI commands) to collect ALL installed package versions from the lockfile — gives full transitive coverage across all 4 package managers. Workspace package names are filtered out via `collectWorkspacePackageNames` to avoid failed registry lookups. Persists ALL installed packages to scan_results — direct, dev, peer, optional classified from package.json sections (priority: dependency > devDependency > peerDependency > optionalDependency), everything else = transitive. Transitive deps stored with `registryResolved=0` and null latestVersion/latestInRange/upgradeType (resolved by background transitive-resolve job). `DependencyKind` type: `"dependency" | "devDependency" | "peerDependency" | "optionalDependency" | "transitive"`. `IScanServiceDependency` has `dependencyKind`, `registryResolved: boolean`, nullable `latestVersion`/`latestInRange`/`upgradeType`. Health score calculation filters to `registryResolved` deps only.
- scan_results table: `id`, `projectId`, `name`, `currentVersion`, `latestVersion` (nullable), `latestInRange` (nullable), `type`, `upgradeType` (nullable), `dependencyKind` (NOT NULL, default "dependency"), `registryResolved` (integer, NOT NULL, default 1), `scannedAt`. upgrade_jobs table has `progress` (nullable integer 0-100) and `progressLabel` (nullable text) for job progress reporting.
- `classifyUpgrade` shared utility at `src/shared/versions/types.ts` — classifies version diff as patch/minor/major/none using semver. Used by ScanService and TransitiveResolveJobExecutor. Validates semver before diffing.
- Scan is async: `POST /scan` enqueues a job, returns `{jobId}`. JobWorker executes scan, persists results to `scanResults` table, broadcasts WS progress events (`scan:progress`, `scan:complete`, `scan:failed`). ScanJobExecutor reports job progress via `context.setProgress()` at 6 phase boundaries (0-95%) and logs at each phase via `appendLog` (start, package counts, results saved, vulnerability scan, license scan, graph refresh, final summary with health score). ScanJobExecutor detects when scan returns 0 results but package.json has dependencies — stores a warning message on the job row and includes it in the `scan:complete` WS payload.
- TransitiveResolveJobExecutor (job type "transitive-resolve"): background job that resolves registry data for transitive deps. Queries scan_results with registryResolved=0, batch registry lookups via RegistryCacheService (LOOKUP_CONCURRENCY=10), updates rows with latestVersion/latestInRange/upgradeType/registryResolved=1. Per-package error handling — each registry lookup is wrapped in its own try/catch; a failed package is logged (`Failed to resolve {name}: {message}`), still marked `registryResolved:1` (so it doesn't get retried forever) but with `latestVersion`/`latestInRange`/`upgradeType` left untouched (only `registryResolved` and `scannedAt` are set) — one bad package no longer aborts the whole batch. Always updates `scannedAt = Date.now()` on every resolved row (success or failure), which is what the TTL staleness sweep (below) keys off of. Reports progress via setProgress. Broadcasts `transitive-resolve:complete` with `{ projectId, resolved, failed }` — `failed` is the count of packages that errored during this run. Chained automatically by JobWorker after scan jobs when unresolved transitive deps exist (`chainTransitiveResolveAfterScanIfNeeded`).
- Job progress: `IJobExecutionContext.setProgress(input: ISetProgressInput)` — broadcasts `job:progress` WebSocket event on every call, DB writes throttled to 1/sec. `finishJob` sets progress=100 only if executor used setProgress. UI JobProgressPanel renders Mantine Progress bar + label above logs when progress is not null. Indeterminate (null progress) shows existing spinner behavior.
- Dependencies route: `GET /api/projects/:id/dependencies?dependencyKind&registryResolved` — filters by dependencyKind (all/dependency/devDependency/peerDependency/optionalDependency/transitive) and registryResolved (all/true/false). Response includes dependencyKind and registryResolved fields, nullable latestVersion/upgradeType.
- Transitive resolve status: `GET /api/projects/:id/transitive-resolve-status` — returns total/resolved/pending counts for transitive deps.
- Packages route: `GET /api/packages` now supports `dependencyKind` query filter. UI packages page has dependencyKind filter dropdown + "Pending" badge for unresolved deps.
- Project detail DependencyTable: Kind column with colored badges (Direct=blue, Dev=grape, Peer=cyan, Optional=orange, Transitive=gray), "Resolving..." for unresolved deps, disabled checkbox for unresolved.
- Dependency graph page: auto-refreshes on `scan:complete` and `transitive-resolve:complete` WebSocket events (previously manual only). Nodes show colored dependency kind dots (same color scheme as DependencyTable badges).
- Install route: `POST /api/projects/:id/install` with `{ flags?: string[] }`. `GET /api/install-options/:packageManager` returns available flags from the driver. Project API responses include `hasNodeModules: boolean` (computed via `existsSync`).
- SecurityService: config-driven, reads checks from `pmSecuritySettings` table per project's PM. Results stored as JSON blob in `securityChecks.results`
- Settings routes: CRUD on `pmSecuritySettings` table (`GET/POST /api/settings/security`, `PUT /api/settings/security/:id`, `PATCH /api/settings/security/:id/toggle`, `POST /api/settings/security/reset`). Settings have an `enabled` column — disabled settings are skipped during security checks. POST validates against `SECURITY_FIELD_REGISTRY` (rejects unknown PM/field, validates expectedValue via Zod). Derives configFile from registry. Reset endpoint deletes all rows for a PM and re-creates from registry defaults atomically.
- PackageManagerService: detects PM by lockfile (yarn.lock/pnpm-lock.yaml/bun.lock/package-lock.json — throws if none found), manages version queries and updates. Delegates to PackageManagerDriverRegistry for all PM-specific commands.
- PackageManagerDriver: pure strategy interface — each PM (yarn/npm/pnpm/bun) has a driver that describes CLI commands and parses output. Drivers have no I/O or DI deps. Adding a new PM = one driver file + register in PackageManagerDriverRegistry. BunDriver uses `npm view` for registry lookups (bun has no built-in equivalent) and parses `bun pm ls` tree output. Each driver also defines `installFlags()` (available CLI flags with metadata), `installCommand(flags)`, and `refreshTransientCommand(packageNames?)` — optional targeted refresh (e.g. `yarn up aws-sdk -R` vs `yarn up ** -R`). `parseRegistryInfo` extracts `repoUrl` (normalized GitHub URL), `repoDirectory` (npm `repository.directory` for monorepo subpath), and `license` (SPDX identifier) via `normalizeRepoUrl`/`extractRepoDirectory` helpers.
- PackageManagerDriverRegistry: singleton Map holding all drivers in detection priority order (yarn → pnpm → bun → npm). Services depend on registry, not drivers directly.
- SecurityService: `parseConfigFile` supports YAML (.yml/.yaml), JSON (.json — for package.json checks), TOML (.toml — for bunfig.toml, flattens nested keys with dots), and flat key=value (.npmrc). Uses `smol-toml` for TOML parsing.
- `seedSecurityDefaults` runs on startup after migrations. For each PM in `SECURITY_FIELD_REGISTRY`, inserts default rows if none exist. Idempotent — safe to run every startup.
- Project export/import: `GET /api/projects/export` returns `[{path}]`, `POST /api/projects/import` accepts same format, adds each project with auto-scan, skips existing paths.
- Clone route: `POST /api/projects/clone` validates URL (https/git@ only), extracts repo name, enqueues clone job. Folder name sanitized against path traversal.
- Filesystem browse: `GET /api/filesystem/browse?path=X&showHidden=true` returns directory listings with `currentPath` in response (resolved via `realpath()`, defaults to `process.cwd()`).
- Filesystem scan: `GET /api/filesystem/scan?path=X&depth=N` scans for projects with `package.json`. Workspace-aware: if root `package.json` has `workspaces` field, resolves workspace globs directly (ignores depth). Otherwise recurses to `depth` (default 1, max 5). Excludes `node_modules`/`.git`/hidden dirs, filters out already-added projects from DB. Returns `{ items, total, scannedPath, scannedCount, filteredCount, mode }` where `mode` is `"workspaces"` or `"depth"`. Custom `globWorkspacePattern` implementation (no external glob dependency).
- Normalized dependency schema: three tables — `dependencies` (global package registry, name UNIQUE, `repoUrl`, `repoDirectory`), `dependencyVersions` (per-package versions with publishedAt), `changelogs` (one-to-one with dependencyVersions, denormalized dependencyId for direct queries). ScanJobExecutor upserts into all three during scan. `content = null` means unfetched, empty string means fetched with no content found. `repoDirectory` stores npm `repository.directory` for monorepo CHANGELOG.md lookups.
- ChangelogService: resolver chain pattern — tries GitHubReleasesResolver (via `gh api`), ChangelogFileResolver (CHANGELOG.md via `gh api`), NpmReadmeResolver (readme from registry cache). First non-empty result wins. Resolvers never throw — return empty Map on failure. Update guard: only writes rows where `content IS NULL`. Monorepo support: GitHubReleasesResolver matches `packageName@version` tags, ChangelogFileResolver uses `repoDirectory` from npm registry (highest priority), then root, then `packages/<unscoped>/CHANGELOG.md` for scoped packages. `repoDirectory` threaded from npm `repository.directory` through drivers → registry cache → dependencies table → resolver interface. Prerelease versions (containing `-`) filtered at scan time, executor, and query. `compareVersions()` exported for reuse by ChangelogJobExecutor and changelog route dedup.
- ChangelogJobExecutor: resolves changelogs asynchronously for a version range. Input: `{ packageName, from, to }` via packages JSON. Only resolves stable versions in range (not all unfetched). Broadcasts `changelog:resolved` WS event per version as each resolves. Uses createImplementation pattern with DI — receives resolvers via `[ChangelogResolver, { multiple: true }]`. Dependencies: DatabaseClient, ChangelogResolver[], WebSocketBroadcaster.
- Changelog routes: `GET /api/changelogs/:packageName?from=X&to=Y` — returns cached entries immediately (non-blocking), auto-enqueues changelog job if unfetched versions exist. Dedup by packageName AND version range — when active job exists, compares `to` versions; if requested range extends beyond active job, enqueues supplementary job for the gap. Response: `{ items, total, resolving }`. Short-circuits when `from === to`. `POST /api/changelogs/:packageName/re-resolve` — resets `source='none'` rows, uses same `enqueueChangelogIfNeeded` shared helper as GET (range comparison, supplementary job for uncovered gap, malformed JSON fallback), returns `{ resolving: true }`.
- Dashboard routes: `health_snapshots` table stores daily health scores per project (upserted by ScanJobExecutor after every scan), including `vulnerabilityCritical`/`vulnerabilityHigh`/`vulnerabilityModerate`/`vulnerabilityLow` daily counts. `GET /api/dashboard/health` — current snapshot per project with summary (totalProjects, averageScore, worstProject), scoreDelta vs 7 days ago, sorted worst-first. `GET /api/dashboard/health/trend?range=7d|30d|90d|all` — historical snapshots grouped by project, alphabetical. `GET /api/dashboard/activity` — last 20 jobs across all projects. `GET /api/dashboard/staleness` — projects sorted by lastScannedAt ascending (nulls first). `GET /api/dashboard/security` — aggregate pass/fail from latest securityChecks per project, sorted by passing ratio ascending. `GET /api/dashboard/vuln-trend?days=7|30|90` — aggregated vulnerability counts per date from healthSnapshots, SUM grouped by date, ordered ascending.
- Packages route: `GET /api/packages?search=X&upgradeType=X&projectId=X&hasChangelog=true&page=N&pageSize=N&sortBy=name|lastPublishedAt&sortOrder=asc|desc` — SQL aggregation with `json_group_array`/`json_object`, pagination via `LIMIT/OFFSET`, separate `COUNT(*)` query for total. Joins scanResults + projects + changelogs + dependencyVersions. Response includes `resolvedChangelogCount` (changelogs with actual content) and `totalChangelogCount` (all changelog records including unfetched/failed). UI ChangelogButton shows "Changelog (3+2)" for resolved+pending split; hidden when `totalChangelogCount === 0`.
- ScanService version resolution: uses `semver` package for upgrade classification. Prerelease versions (rc, alpha, beta, etc.) are filtered out — only stable versions considered as upgrade targets. When dist-tags.latest points to a prerelease, falls back to the last stable version in the versions array. When registry reports a version lower than current (downgrade), latestVersion is clamped to currentVersion.
- All dependencies stored: ScanService returns ALL deps (including up-to-date with `upgradeType: "none"`), not just outdated ones. Project detail page has upgrade filter (all/upgradeable/up-to-date).
- Per-package rescan: `POST /api/packages/:packageName/rescan` clears registry cache for one package, re-fetches, updates all scan results referencing it.
- App settings: `app_settings` table (key/value), `GET /api/settings/app`, `PUT /api/settings/app/:key`. `seedAppSettings` runs on startup — seeds `branch_template`, `commit_template`, `log_level` with `onConflictDoNothing`. `log_level` editable in UI via dropdown (error/warn/info). Template tokens: `${YYYY}/${MM}/${DD}/${BRANCH}/${PROJECT}`. List endpoint returns `configSource: "db" | "file" | "error"`, `fileManaged: string[]`, and optional `configError` — when global `.dependency-upgrader.json` has a `settings` section, file values override DB for managed keys. AppSettings page shows read-only banner and disables editing for file-managed keys.
- Backup: `GET /api/projects/backup` returns `.zip` file (fflate) containing `backup.json` with appSettings, securitySettings, projects, dependencies (with versions and changelogs), registryCache. `POST /api/projects/backup` accepts `.zip`, imports with `onConflictDoNothing`. UI at `/backup` page. Gzip compression enabled via `@fastify/compress` (Vite proxy strips Accept-Encoding to prevent double-compression in dev).
- GitService: abstraction for git operations (getCurrentBranch, createAndCheckoutBranch, checkout (switches to an existing branch, unlike createAndCheckoutBranch's `-b`; used by AutoFixPrJobExecutor to return to the original branch between PR attempts), getStatus, stageAll, commit, push). Uses CommandRunner, not exposed as standalone routes — used by step resolvers (BranchResolver, CommitResolver, PushResolver, PrResolver) and AutoFixPrJobExecutor.
- ForgeService: GitHub/GitLab PR creation. detectForge() parses git remote URL (github.com/gitlab.com). createPr() uses @octokit/rest (GitHub) or @gitbeaker/rest (GitLab) with encrypted tokens from app_settings (github_token/gitlab_token), decrypted via EncryptionService. parseRemoteUrl() extracts owner/repo from HTTPS and SSH remote URLs.
- ScanSchedulerService: bree-based scheduled auto-scan. Per-project interval overrides stored in scan_schedules table, global default in app_settings (scan_schedule_default). Preset intervals: 6h/12h/24h/48h/weekly/disabled. Emits "scan:scheduled" via EventBus (server.ts wires to JobWorker.enqueue). Subscribes to "scan:completed" to update lastRunAt/nextRunAt. Staggered boot recovery for past-due scans.
- EventBus: typed pub/sub service wrapping Node EventEmitter. IEventMap interface extensible via `declare module` augmentation — each service declares its own events. Breaks circular DI dependencies (ScanSchedulerService no longer depends on JobWorker directly). Events: "scan:completed" (emitted by ScanJobExecutor), "scan:scheduled" (emitted by ScanSchedulerService).
- VulnerabilityService: orchestrates PM audit + OSV.dev enrichment. Merges by dedup_key (CVE ID or hash fallback). scan() accepts optional `allInstalledVersions: Map<string, string>` for populating installedVersion on transitive dependencies (audit reports packages not in scan_results). scan() also reads `dependencyKind` per package from `scan_results` and stores it on each vulnerability row (see `vulnerabilities` table below). Health score penalty: critical*10 + high*5 + moderate*2 + low*1, subtracted from freshness-based score. Stored in vulnerabilities table with (project_id, package_name, dedup_key) unique constraint. `getSummary(options?)` additionally returns `transitiveCount`/`directCount` (split of the (non-dismissed) result set by `dependencyKind === "transitive"` vs not) alongside `totalVulnerabilities`/`counts`/`projectSummaries` — surfaced on the dashboard by `VulnerabilitySummaryWidget` as a "N direct, M transitive" breakdown line. Dismiss/snooze: `dismissedAt`/`dismissedUntil`/`dismissedBy` columns. `bulkDismiss(ids)`, `bulkSnooze(ids, days)`, `bulkUndismiss(ids)`, `getProjectIdsForVulnerabilityIds(ids)`. Query-time snooze expiry (no cron). Filters: `projectIds`, `includeDismissed`, `ids`, `scannedDate` (YYYY-MM-DD, filters by UTC day range). getSummary excludes dismissed. scan() uses upsert (INSERT ON CONFLICT DO UPDATE) + stale-sweep to preserve dismiss state across rescans. `transferDismissState()` detects dedupKey changes via advisory URL + package name matching and copies dismiss/snooze fields to new records before upsert (handles CVE assignment after initial scan). `getById(id)` returns single vulnerability joined with project name. `getRecentlyExpiredSnoozes(sinceMs)` returns vulnerabilities with snooze expired since given timestamp. `enrichAndSort({ items, options? })` — post-query pipeline: enriches raw vulnerabilities with projectName + dependencyKind (reads dependencyKind from the stored column, no scanResults join), filters by dependencyType (all/direct/transitive), sorts by severity/packageName/projectName with asc/desc, paginates when page + pageSize provided. Returns `{ items, total }`. Used by all three vulnerability route handlers (list, per-project, export). Severity sort: VULNERABILITY_SEVERITIES index order (critical=0, info=4), desc = most-severe-first.
- OsvCacheService: batch query + TTL cache. `getEnrichedDetail(osvId)` fetches full OSV advisory for detail page (description, references, affected versions with pairwise event parsing, CVSS score/vector, aliases). Returns null on fetch failure.
- Vulnerability routes: `GET /api/vulnerabilities?severity&packageName&source&projectIds&includeDismissed&scannedDate&dependencyType&page&pageSize&sortBy=severity|packageName|projectName&sortOrder=asc|desc` — list with optional filters (scannedDate validated with z.string().date()). All vulnerability responses include `dependencyKind: string` (stored in the vulnerabilities table, set at scan time from scanResults). `dependencyType` filter (`all`/`direct`/`transitive`) applied server-side after enrichment via `filterByDependencyType`. `GET /api/vulnerabilities/:vulnerabilityId/detail` — single vulnerability with OSV enrichment (description, references, affected versions, CVSS). `GET /api/vulnerabilities/expired-snoozes?since=<ms>` — recently expired snoozes for notification. `GET /api/vulnerabilities/:projectId?severity&packageName&source&projectIds&includeDismissed&scannedDate&dependencyType&page&pageSize&sortBy&sortOrder` — per-project list with same sort/page/filter params as main list route. `GET /api/vulnerabilities/summary` — dashboard aggregation (excludes dismissed). `POST /api/vulnerabilities/:projectId/scan` — trigger rescan. `POST /api/vulnerabilities/osv/refresh` — invalidate OSV cache. `PATCH /api/vulnerabilities/bulk` — dismiss/snooze/undismiss (Zod discriminated union, snoozeDays required for snooze). `POST /api/vulnerabilities/bulk/rescan` — resolve unique projects from vulnerability IDs, scan each. `GET /api/vulnerabilities/export?format=csv|json&ids=...` — export with filters, Content-Disposition attachment.
- Snooze expiry: server-side `setInterval` in server.ts queries `getRecentlyExpiredSnoozes`, broadcasts `snooze:expired` via WebSocket. Interval configurable via `snooze_check_interval` app setting (default 1h, options 15m/30m/1h/4h, requires restart). Frontend `SnoozeExpiryListener` in App.tsx shows Mantine toast. Presenter also checks on page load (5-minute lookback). Toast dedup via 60s high-water-mark.
- AuditParserService: normalizes npm/yarn/pnpm/bun audit JSON into IAuditVulnerability[]. Handles all 4 PM-specific formats internally.
- OsvCacheService: OSV.dev batch query with 24h TTL (configurable via OSV_CACHE_TTL_MS env), concurrency dedup via in-flight promise map, configurable invalidation (by package, list, all, age). CVSS v3/v2 vector parsing for severity mapping.
- License compliance: three tables — `licenses` (per-project package license, one row per (projectId, packageName), UNIQUE constraint, `source: "registry" | "license-checker"`, `riskTier` classified via `classifyLicenseRiskTier`), `license_policy_rules` (glob-based `licensePattern`/`packagePattern` matching via `picomatch`, `action: allow|warn|deny`, `priority`, optional `projectId` for project-scoped overrides vs global rules), `license_violations` (one row per license/rule match, UNIQUE(licenseId, ruleId), cascades on delete from either parent). LicenseCheckerService resolves licenses from npm registry metadata via RegistryCacheService — reads packages from `scan_results` table, fetches `license` field from cached registry info, no external CLI tools needed. LicensePolicyService.evaluate(projectId, licenseInputs) loads global + project-scoped rules, matches each license's SPDX id (splitting `OR` expressions into components) against rules by glob pattern; the most permissive matching component wins for OR expressions, highest-`priority` then project-scoped-over-global wins ties; persists violations to `license_violations` as a side effect (replacing prior violations for re-evaluated licenses) — license inputs with no corresponding `licenses` row are evaluated in-memory only and not persisted (supports dry-run use). `getComplianceStatus(projectId)` returns total/allowed/warned/denied counts. License scanning is integrated into ScanJobExecutor (no separate job type) — after dependency scan + vulnerability scan, calls LicenseCheckerService.scan() to resolve licenses from registry cache, upserts into `licenses`, sweeps stale rows, evaluates policies, records license_snapshots, broadcasts `license-scan:complete`, and emits `license-scan:completed` event.
- Auto-fix PRs: two tables — `auto_fix_settings` (one row per project, UNIQUE(projectId): `enabled`, `upgradeTypes` (JSON array, default `["patch"]`), `groupingStrategy` (`per-package` default, or `per-project`/`per-upgrade-type`), `branchPrefix` (default `auto-fix/`)), `auto_fix_pull_requests` (one row per generated branch/PR, UNIQUE(projectId, branchName): `packageNames`/`fromVersions`/`toVersions` JSON, `upgradeType`, `branchName`, `prUrl`, `prNumber`, `status` (`pending`|`created`|`merged`|`closed`|`failed`), `licenseWarnings` JSON or null). AutoFixSettingsService: `getSettings`/`getSettingsOrDefaults` (in-memory defaults when no row exists, `id: ""`)/`updateSettings` (upsert). AutoFixPrService.generateForProject(projectId): reads `settings.upgradeTypes` to filter `scanResults` candidates, evaluates each candidate's license via LicensePolicyService (skips packages with a `deny` violation into `skippedDeny`, attaches `warn` violations as `licenseWarnings`), skips packages already covered by an open (`pending`/`created`) PR into `skippedDuplicate`, groups remaining packages per `groupingStrategy` (per-package: one PR per package; per-project: one PR for everything; per-upgrade-type: one PR per patch/minor/major bucket), and inserts `pending` rows per group — replacing any stale (`failed`/`merged`/`closed`) row on the same branch name first, since `(projectId, branchName)` is unique. `buildPrBody()` renders a markdown PR description (upgrade table, changelog excerpts, license warnings). AutoFixPrJobExecutor (job type `auto-fix-pr`): calls `generateForProject`, then for each `pending` record checks the working tree is clean (throws if dirty), saves the original branch, and per record: creates+checks out the branch, upgrades each package via UpgradeService, stages+commits, pushes via GitService, creates a PR via ForgeService (throws if no forge configured), and updates the record's status to `created` (with `prUrl`/`prNumber`) or `failed` on any error — always checking back out to the original branch in a `finally` block (best-effort). Broadcasts `auto-fix:progress` (per package, per record) and `auto-fix:complete` (`created`/`skipped`/`failed` counts) via WebSocket.
- Auto-chain (auto-fix): `scan:completed` (emitted by ScanJobExecutor via EventBus, which includes license scan) is subscribed in `server.ts` — if the project's `AutoFixSettingsService.getSettings(projectId)` has `enabled: true`, auto-enqueues an `auto-fix-pr` job. Opt-in only.
- Dependency graph: `dependency_edges` table (one row per parent→child edge: `projectId`, nullable `parentPackage`/`parentVersion` (null = root/direct dependency), `childPackage`, `childVersion`, `dependencyType` (`dependency`/`devDependency`), `depth`, `scannedAt`). Fully replaced on each refresh (delete-then-insert in a transaction, keyed by `projectId`). `LockfileParserService.parse(projectPath, packageManager)` picks the parser by package manager and returns `DependencyEdge[]` without touching the DB — never throws, returns `[]` on missing/unparsable lockfile or unknown package manager. Four format-specific parsers, each BFS-walking from the root `package.json` dependencies/devDependencies down through the lockfile's own dependency graph (visited-set guarded, so cycles/diamonds are only expanded once): npm (`parsePackageLock`, walks `package-lock.json` v2/v3 `packages` map by `node_modules/...` path depth), yarn (`parseYarnLock`, splits `yarn.lock` into blocks, maps every descriptor — `name@range` — to its resolved entry), pnpm (`parsePnpmLock`, YAML-parsed via the existing `yaml` package, walks `importers` for root deps then `packages` for transitive deps, package keys are `name@version`), bun (`parseBunLock`, JSON-with-`//`-comments via a small `stripJsonComments` helper, walks `workspaces` for root deps then `packages` tuples `[resolution, metadata]` for transitive deps).
- `DependencyGraphService`: `getGraph(projectId)` reads all `dependency_edges` rows for the project and derives `rootPackages` (edges with `depth === 0`), `totalPackages` (distinct `childPackage`), `maxDepth`, `edgeCount` — no separate summary table, stats are always derived from edges. `findPaths(params: IFindPathsParams)` (object param: `{ projectId, packageName }`) builds an adjacency map (`parentPackage → edges[]`) from `getGraph()` and BFS-walks from every root edge, extending a `chain` of `{packageName, version}` nodes with a per-branch visited-set (so the same package can appear via multiple independent paths, but never twice within one path/cycle) until it collects every path that reaches `packageName`, returned as `IDependencyPath[]`. `searchPackages(params: ISearchPackagesParams)` (`{ projectId, query, limit? }`, default `limit: 20`) — `SELECT DISTINCT childPackage FROM dependency_edges WHERE projectId = ? AND childPackage LIKE '%query%' ESCAPE '\'`, ordered alphabetically; LIKE wildcards (`%`, `_`, `\`) in query are escaped. Returns `[]` for a blank query. Used to power the GraphPage search autocomplete without loading the full graph client-side. Autocomplete dropdown: `closeSuggestions()` hides dropdown without clearing search query (Escape key, click-outside); `clearSearch()` resets everything (X button). `refreshGraph(projectId, projectPath, packageManager)` calls `LockfileParserService.parse`, then in one transaction deletes existing edges for the project and bulk-inserts the freshly parsed ones (each row gets a generated id and `scannedAt = Date.now()`); returns the new edge count and no-ops the insert (but still clears old edges) when the parse yields zero edges.
- Dependency graph routes (`src/api/routes/dependencyGraph.ts`, defs in `src/shared/routes/dependencyGraph.ts`): `GET /api/dependency-graph/:projectId` returns the full graph, or — when `?package=<name>` is given — `{ paths }` from `findPaths` instead (same route, response is a Zod union). `GET /api/dependency-graph/:projectId/packages?query&limit` returns `{ packages: string[] }` from `searchPackages` — feeds the GraphPage autocomplete. `POST /api/dependency-graph/:projectId/refresh` re-parses the lockfile on demand (404 if project missing, 400 if no package manager detected yet) and returns `{ edgeCount }`. `GET /api/dependency-graph/:projectId/stats` returns `{ totalPackages, maxDepth, rootCount, edgeCount }` (derived from `getGraph`, no dedicated stats query).

License policy routes (`src/api/routes/licensePolicies.ts`): `GET/POST /api/license-policies` (list with optional projectId filter, create), `PUT/DELETE /api/license-policies/:id` (update — 404 if missing, merges partial body over existing row; delete always returns `{deleted: true}`).
- Upgrade wizard (API-first): session-based multi-step upgrade flow. `upgrade_sessions` table tracks state. 7 ordered steps: select-packages, branch, upgrade, refresh-transient, commit, push, create-pr. Step resolver registry maps type to resolver class. Each step executed via `POST .../steps/:stepType/execute` or skipped via `.../skip`. Required steps (select-packages, upgrade) cannot be skipped. Session status: active/completed/aborted. API designed for both UI and AI agent automation. - Minimal age gate enforcement: ScanJobExecutor reads age gate from `pmSecuritySettings`, passes duration to ScanService. `resolveLatestVersion` filters versions by publish time. Defined for all PMs: Yarn (`npmMinimalAgeGate`), npm (`minimal-age-gate`), pnpm (`minimumReleaseAge` in minutes), bun (`minimal-age-gate`).
- Auto-scan after install/upgrade/transient: `chainScanAfterJobIfNeeded` in JobWorker enqueues scan job after install, dependency, and transient jobs complete. Packages page listens for `scan:complete` WS event and auto-reloads.
- Transitive resolve TTL: `chainTransitiveResolveAfterScanIfNeeded` (JobWorker) calls `markStaleTransitiveDepsUnresolved` before checking for unresolved rows — reads the `transitive-resolve-ttl` app setting (hours; default `24`, seeded by `seedAppSettings`; `0` disables the sweep entirely), and for every `transitive` scanResults row that's `registryResolved:1` with `scannedAt` older than `now - ttlHours`, flips it back to `registryResolved:0` so the subsequent transitive-resolve job re-checks it against the registry. This is what keeps long-lived transitive version data from going stale between scans — a package resolved 3 days ago under a 24h TTL gets re-resolved on the next scan even though its scan_results row itself wasn't touched. Editable in AppSettings UI (`AppSettingsPresenter.KNOWN_SETTINGS["transitive-resolve-ttl"]`, dropdown: Disabled/12h/24h/3d/7d).
- AppLogService: configurable log level (`log_level` app setting, default `warn`). Validated against `SECURITY_FIELD_REGISTRY` + `INSTALL_FLAG_REGISTRY`. Full-replace-per-PM semantics for security. `InstallJobExecutor` reads file flags, `RegistryCacheService` passes registry URL to drivers, `UpgradeService` applies version prefix (default `caret`). `GET /api/settings/pm` returns all 4 PMs with merged flags + general settings.

- Node.js engine (EOL) checks: `#shared/engines/` holds the classification core shared by both API and CLI — `parseEnginesNode(range)` extracts the minimum major version from an `engines.node` semver range (e.g. `">=16"` → `16`, `null` for unparseable/absent ranges), `classifyNodeVersion({ majorVersion, schedule })` maps a major version against an `INodeRelease[]` schedule into `EngineStatus` (`"current" | "active-lts" | "maintenance" | "eol" | "unknown"`) + `eolDate`, `NODE_RELEASES` (`#shared/engines/nodeReleases.ts`) is a hand-maintained embedded fallback schedule used when no live data is available, and `walkNodeModules({ nodeModulesPath, onMalformedPackage? })` is the shared node_modules walker (symlink-cycle dedup via realpathSync, scoped package handling, .bin skip) returning `Map<string, INodeModulesPackageEntry>` — used by both EngineService (API) and CheckEnginesStep (CLI).
- `engine_checks` table (`id`, `projectId` FK cascade, `packageName`, `enginesNode` nullable, `minimumMajor` nullable, `status`, `eolDate` nullable, `scannedAt`; UNIQUE(projectId, packageName)) — one row per scanned package per project; the project's own root `package.json` is stored with `packageName: ""`. `node_release_data` table (`id`, `version` UNIQUE, `codename` nullable, `releaseDate`, `ltsStart` nullable, `maintenanceStart` nullable, `eolDate`, `fetchedAt`) caches the Node.js release schedule fetched from the endoflife.date API.
- `NodeReleaseDataService.getSchedule()`: DB-cached (24h TTL keyed off `fetchedAt`) wrapper around `GET https://endoflife.date/api/nodejs.json`. Fresh cache rows are returned as-is; on a stale/empty cache it fetches live, upserts into `node_release_data` (`onConflictDoUpdate` by `version`), and returns the fetched schedule. A fetch failure falls back to existing (stale) cache rows if any exist, otherwise to the embedded `NODE_RELEASES` fallback — never throws.
- `EngineService` (`src/api/services/Engine/`): `scan({ projectId, projectPath, warnMaintenance? })` reads the root `package.json`'s `engines.node` plus walks `node_modules` via the shared `walkNodeModules` utility from `#shared/engines/`, classifies each against `NodeReleaseDataService.getSchedule()`, and upserts into `engine_checks` (`onConflictDoUpdate` by `(projectId, packageName)`, then deletes stale rows from prior scans via a `scannedAt` low-water-mark, same pattern as `dependency_edges`/vulnerabilities). When `warnMaintenance` is `false` (default `true`), maintenance-status dependency findings are excluded before persistence — root finding is never filtered. Returns `{ rootStatus, rootEnginesNode, findings, summary }`. `getByProject(projectId)` lists all `engine_checks` rows for a project. `getSummary(options?: { projectIds? })` aggregates root status + dependency status counts (`IEngineStatusCounts`: eol/maintenance/activeLts/current/unknown) per project, joined with project names, optionally filtered to a project subset.
- `EngineScanJobExecutor` (job type `engine-scan`): thin wrapper — calls `EngineService.scan()`, broadcasts `engine-scan:complete` (`{ projectId, counts }`), logs a one-line summary via `context.appendLog`.
- Engine routes (`src/api/routes/engines.ts`, defs in `src/shared/routes/engines.ts`): `GET /api/engines/summary` (aggregate status counts + per-project summaries — registered before `:projectId` to avoid path shadowing), `GET /api/engines/releases` (cached Node.js release schedule via `NodeReleaseDataService.getSchedule()`), `GET /api/engines/:projectId` (engine checks for one project), `POST /api/engines/:projectId/scan` (404 if project missing, otherwise runs `EngineService.scan()` synchronously and returns the result — unlike the dependency/vulnerability/license scans, this one is not job-queued since a full engines walk is cheap).

### CLI Layer

- Entry point `src/cli/index.ts` (`#!/usr/bin/env node`, bin name `depco`): registers `tsx/esm/api` (`register()`) as the very first two lines, before any other import — enables dynamic `import()` of `.ts` files (e.g. `depco.config.ts`) at runtime without a separate build step. Then builds a DI container via `createContainer()`, wires the whole CLI dependency tree with `registerFeatures(container, [CliFeature])` (walks `dependencies` recursively, registering each feature exactly once — not `CliFeature.register(container)` directly), resolves `StepRunner`, then defines three `yargs` commands, `init`, `start`, and `scan`. Each command handler resolves its `Command` abstraction (`InitCommand` / `StartCommand` / `ScanCommand`) from the container and runs it: `await runner.run({ steps: command.steps(), context: command.context() })`. `scan` declares `--check` (choices: license/vulnerability/engines/all, default: license) and `--format` (choices: table/json/csv/sarif, default: table). Options forwarded to `command.context(argv)` and consumed by CheckVulnerabilitiesStep/CheckEnginesStep (skip logic — each runs only for its own check name or `all`) and RenderOutputStep (formatter selection).
- `Command` abstraction (`src/cli/commands/abstractions/Command.ts`): `ICommand` interface with `steps(): Step.Interface[]` and `context(): Step.Context`. `InitCommand`, `StartCommand`, and `ScanCommand` are all `createAbstraction<Command.Interface>(...)` aliases of the same interface, registered under distinct DI tokens (`Cli/InitCommand`, `Cli/StartCommand`, `Cli/ScanCommand`).
- `StepRunner` (`src/cli/runner/`): `IStepRunner.run({ steps, context })` executes `Step.Interface[]` sequentially against a shared mutable `Step.Context`, rolling back already-executed steps (in reverse order, best-effort) if a later step throws. Each `Step.Interface` has `run(context)` and optional `rollback(context)`.
- `InitCommandFeature` (`src/cli/commands/init/feature.ts`) composes 7 step features via `dependencies` (not manual `.register()` calls): `EnsureDataDirectory`, `RunMigrations`, `GenerateEncryptionKey`, `SelectPort`, `CreateAdminUser`, `WriteEnvFile`, `PrintNextSteps` — each its own DI-wired step in `steps/<StepName>/` (abstraction + implementation + feature.ts). Its own `register()` only binds `InitCommand` itself; the step features are registered by `registerFeatures` walking the tree.
- `StartCommandFeature` (`src/cli/commands/start/feature.ts`) composes `ValidateEnvironment` and `StartServer` step features the same way; `StartServerStep` wraps the refactored `src/api/server.ts` bootstrap (extracted into a reusable function so both `yarn start` and `depco start` share one code path).
- `ScanCommandFeature` (`src/cli/commands/scan/feature.ts`) composes `DetectPackageManager`, `LoadConfig`, `ParseLockfile`, `CheckLicenses`, `CheckVulnerabilities`, `CheckEngines`, and `RenderOutput` step features plus `OutputFormatterFeature`, run in that order. `ScanCommand.context(argv?)` uses `process.cwd()` as `dataDirectory`, forwards `--check` and `--format` options to `context.options`. `CheckLicensesStep` returns `success: true` even with violations (stores them in context.results for RenderOutputStep). `CheckVulnerabilitiesStep` runs audit + OSV via shared services, skips if `--check` doesn't include vulnerability. `RenderOutputStep` collects all findings, builds IScanOutput, calls OutputFormatterFactory to create the right formatter, outputs to stdout, and sets `process.exitCode = 1` on license violations, a root-level EOL engines finding, or vulnerabilities exceeding maxSeverity threshold (checked in that order — license first). Exit codes: 1 for any license violation, 1 when the root package's `engines.node` classifies as EOL, 1 for vulnerability severity >= config maxSeverity.
- `CheckEnginesStep` (step name `check-engines`, `src/cli/commands/scan/steps/CheckEngines/`) skips unless `--check` is `engines` or `all`. Reads the project root's `package.json` `engines.node` plus walks `node_modules` via the shared `walkNodeModules` utility, classifies against the embedded `NODE_RELEASES` schedule (no network call, no DB writes), builds `IEnginesFinding[]` (one entry per package, `isRoot: true` for the root), filters out ignored packages AND maintenance-status findings when `config.scan.engines.warnMaintenance` is `false` (root finding never filtered), and stores under `context.results.set("engines", ...)` for `RenderOutputStep`. Malformed package.json files produce findings with `enginesNode: null`.
- `IDepcoConfig.scan.engines` (`#shared/config/schema.ts`): optional `{ ignore?: string[], warnMaintenance?: boolean }` — `ignore` lists package names to exclude (unioned with top-level `scan.ignoredPackages`), `warnMaintenance` (default `true`) controls whether maintenance-status findings appear in output.
- Formatters (`src/cli/commands/scan/formatters/`) all render an `engines` section alongside `license`/`vulnerability`: `TableFormatter` renders a package/engines.node/status/EOL-date table when any engines findings exist, `CsvFormatter` emits one `engines,<package>,...` row per finding, `SarifFormatter` emits one result per finding with `ruleId: engines/<status>`, `JsonFormatter`'s `IScanOutput` includes `findings.engines: IEnginesFinding[]` and `summary.engines: IEngineStatusCounts`.
- `LoadConfigStep` (step name `load-config`, `src/cli/commands/scan/steps/LoadConfig/`) looks for `depco.config.ts` in `context.dataDirectory`. Missing file: sets `context.results.set("config", {})` and returns `{ success: true, skipped: true }` (defaults apply downstream). Found: dynamically imports it via `pathToFileURL(...).href` (works because tsx is registered in `src/cli/index.ts`), validates the default export against `depcoConfigSchema` (`#shared/config/schema.js`), and stores the parsed `IDepcoConfig` under `context.results.get("config")`. Invalid config (Zod failure or import error) returns `{ success: false, message: "Invalid depco.config.ts: ..." }`, which fails the whole scan via `StepRunner`.
- `CheckLicensesStep` reads `context.results.get("config")` (defaulting to `{}` if `LoadConfig` was skipped or ran before this key existed) to derive: `allowedTiers` (`config.scan.license.allowedRiskTiers`, default `["permissive"]`), an ignored-package set merging `config.scan.license.ignoredPackages` and the broader `config.scan.ignoredPackages`, and `registryUrl` (`config.scan.registryUrl`, default `https://registry.npmjs.org`) — passed as an object param into `fetchLicense`/`fetchInBatches` instead of a module-level constant. A result is a violation only if its package isn't ignored AND its risk tier isn't in `allowedTiers`.
- `CliFeature` (`src/cli/feature.ts`) is the top-level compositor: `dependencies: [StepRunnerFeature, InitCommandFeature, StartCommandFeature, ScanCommandFeature]`, empty `register()` body — it exists purely to be the single entry passed to `registerFeatures`, mirroring the "top-level `feature.ts` composes all sub-features" convention used by `ApiFeature` and `PresentationFeature`, except via `dependencies` (declarative walk) rather than imperative `.register()` calls, since none of its own bindings are needed.
- `registerFeatures(container, features)` (`src/shared/di/registerFeatures.ts`): DFS over each feature's `dependencies`, calling `feature.register(container)` post-order exactly once per feature (dedup via a `Set`), throws on dependency cycles. Preferred over manual `Feature.register(container)` chains whenever a feature tree is more than one level deep.
- Package manager detection, DB path (`DB_PATH` env var, default `./data/manager.db`), and `ENCRYPTION_KEY` requirements are unchanged from the API server — `depco init` seeds `data/`, runs migrations, generates the encryption key + `.env`, creates the first admin user, and picks a free port; `depco start` validates the environment then starts the same Fastify server used by `yarn start`.

### UI Rules

- **No inline structural types** — always use named interfaces, even for simple shapes like `Record<string, { label: string }>`. Extract to named interface.
- **All destructive actions require confirmation dialog** — use `ConfirmDialog` from `#ui/infrastructure/Shared/components/ConfirmDialog.js` for any delete/remove action.

### DI Conventions

- Every abstraction in `abstractions/` directory, one file per token
- Namespace with exported types (`Foo.Interface`, `Foo.Record`, etc.)
- `Impl` suffix only on class declaration — never on exports or imports
- Barrel exports: only abstractions and features — never implementations
- All class members need explicit access modifiers

### Testing Rules

- **API tests**: in-memory SQLite, real services, only mock `CommandRunner`
- **UI tests**: mock `HTTPClient` and `WebSocketListener` at DI level, real everything else
- Never `new XxxImpl()` — always resolve through DI container

## Documentation Rules

- All docs go into `docs/` with date-prefixed subdirectories
- Root-level: `README.md`, `CLAUDE.md`, `AGENTS.md`

## Code Exploration

- **Always use CodeGraph first** to locate symbols, trace call paths, and read source.
- **Only fall back to grep/Read** when CodeGraph does not find what you need.
- This rule applies to all agents and subagents equally.

## Subagent Rules

- **Subagents must NEVER spawn new subagents.** Only the main thread may create subagents.
